# Part 01. AI 시대, 왜 프로그래머에게 기획서가 필요한가
- 프로그래머가 ai에게 자연어로 명령을 내려 빠르게 프로토타입을 만드는 시대가 옴
- 그로인하여 명확히 무엇을 만들지 설명하는 능력이 중요해짐
- 해당 파트에서 성명하는 내용 3가지
  - 프로그래머가 왜 기획을 이해해야 하는 가
  - 기획자가 없는 프로젝트에서 어떤 문제가 발생하는 가
  - AI에게 일을 시키기 위해 왜 구조화된 상세 기획서가 필요한 가

 ## Chapter 01. 바이브 코딩 시대의 게임 개발 변화
 - 바이브 코딩의 탄생으로 게임 하나 만드는 데 소모되는 시간과 노력이 줄어듬
 - 바이브 코딩은 완벽한 설계 없이 빠르게 프로토타입을 완성할 수 있음
 - AI는 모호한 아이디어를 정확한 게임으로 바꿔주지 않음
 - 좋은 결과를 얻으려면 사람이 먼저 게임 규칙과 조건을 정리해야함
 - 즉, 프로그래머는 단순히 코드를 작성하는 사람에서 게임의 구조를 설명할 수 있는 사람이 되어야함
 - 이때 필요한 문서가 바로 프로그래머가 쓰는 게임 상세 기획서임
 - 이 책에서 말하는 상세 기획서는 만들 게임에 대해서 명확히 정리하고 AI 이해할 수 있는 형태로 게임을 설명하는 문서

## Chapter 02. 코드를 잘 쓰는 것만으로는 부족한 이류
- 코드를 아무리 잘 써도 무엇을 만들지 명확하지 않으면 좋은 코드도 방향을 잃음
- 기획은 '무엇을 만들 것이가'와 '왜 그렇게 만들어야 하는 가'를 정리하는 일
- 기획이 부족하면 매번 즉흥적으로 프로그래머가 판단하게 되며, 그 결과 기능이 추가될수록 코드 구조도 함께 무너짐
- AI를 활용하는 경우 해당 문제가 더 중요해짐
- 좋은 기획서에서 좋은 프롬프트가 나옴
- 프로그래머가 기획서를 작성해야하는 이유는 구현할 대상을 더 정확히 이해하고, AI와 협업할 때 더 좋은 결과를 얻기 위해서

## Chapter 03. 프로그래머가 기획을 이해해야 하는 순간
- 실제 개발 현장에서는 기획서가 항상 완성된 상태로 전달되지 않기 때문에 프로그래머가 기획을 이해하며, 이를 해결해야 함
- 요구사항이 모호할때 세부 조건을 질문하고 정리하는 능력이 필요하며, 이를 기획 이해력이라 함
  - 예) "플레이어가 공격하면 적이 피해를 입니다" -> "공격 범위는 어디까지인지, 데미지는 언제 적용되는지 등"
- 기능은 각각 따로 존재하지 않고 서로 영향을 주기 때문에 기능 간 충돌이 발생하며, 전체 게임 규칙을 이해해야 올바른 판단을 할 수 있음
- AI에 구현을 요청할 때 프로그래머가 기획 내용을 구현 단위로 설명할 수 있어야함
- 프로그래머가 기획을 이해한다는 것은 게임의 규칙을 구조적으로 읽고, 빠진 조건을 발견하고 , 구현 가능한 형태로 정리하는 능력을 갖춘다는 뜻
- 위에 능력이 있을 때 프로그래머는 단순 구현자를 넘어, 게임의 완성도를 함께 책임지는 개발자가 될 수 있음

## Chapter 04. 기획자가 없는 프로젝트에서 생기는 문제
- 개인 개발이나 소규모 팀 프로젝트에서는 전담 기획자가 없어 프로그래머가 해당 역할을 대신하게 되며, 기능이 늘어날수록 문제가 발생함
- 먼저 생기는 문제는 개발 방향이 자주 바뀌는 것
- 게임의 핵심 재미, 목표, 플레이 루프가 명확하지 않아 필요 없는 기능 자꾸 추가 됨
- 기능이 자꾸 추가되면 프로젝트 범위가 빠르게 커지고, 결국 완성도보다 기능 목록만 늘어나는 상황이 생김
- 두 번째 문제는 기능 간 규칙이 충돌한다는 점
- 각 기능들별로 충돌 나는 부분들은 조건을 미리 정해야함
- 조건을 미리 정하지 않으면 구현 중마다 즉흥적으로 결정하게 됨
- 이런 결정이 쌓이면 코드 구조도 함께 복잡해지고, 나중에는 작은 수정 하나가 여러 시스템에 영향을 주게 됨
- 세 번째 문제는 AI를 황용해도 결과가 불안정해진다는 것
- 기획자가 없다는 것은 AI에게 전달할 기준 문서도 부족하다는 뜻
- "상점 시스템을 만들어줘"라고 요청을 하면 일반적인 코드는 만들어 줄지언정 우리 게임에 맞는 방식으로 제공해 주지 않음
- 결국 사람이 다시 많은 부분을 수정해야함
- 기획자가 없는 프로젝트에서 핵심은 최소한 게임의 핵심 규칙, 기능 범위, 예외 조건, 데이터 구조는 정리해야함
- 프로그래머가 쓰는 상세 기획서는 이런 상황에서 프로젝트의 기준점이 됨
- 더 짧고 명확한 기획서가 필요함

## Chapter 05. AI에게 일을 시키려면 먼저 구조화해야 한다.
- 구현화할 내용을 구조화하여 AI에게 전달해야 더 좋은 결과를 얻을 수 있음
- 구조화란 목적, 조건, 출력 형식, 제한 사항등을 분명하게 하는 것
- 상세기획서에는 AI에게 전달할 구조화된 입력 자료가 되며, 기획서가 없으면 매번 즉흥적으로 작성하게 됨

## Chapter 06. 상세 기획서는 개발을 느리게 만드는 문서가 아니다
- 상세 기획서는 현재 알고 있는 내용을 기준으로 기능의 목적, 규칙, 입력, 출력, 예외 조건을 정리하는 문서임
- 개발 시 기준점이 되는 문서이나, 수정이 불가능 한 것은 아니다.
- 문서가 있으므로써 변견 사항들을 파악하기 쉽고, 변경이 코드에 어떤 영향을 주는지도 더 쉽게 판단할 수 있음
- 상세 기획서가 있으면 AI에게 일일이 설명할 필요가 줄어들며, 개발 속도를 높혀주는 도구가 됨

## Chapter 07. 프로그래머가 쓰는 기획서와 기획자가 쓰는 기획서의 차이
- 기획자가 쓰는 문서는 "무엇이 재미있는가"를 설명한다면, 프로그래머가 쓰는 문서는 "그 재미를 어떤 시스템으로 구현할 것인가"를 설명함
- 프로그래머는 정상적인 흐름 뿐 아니라 비정상적인 흐름도 함께 생각하여 문서를 작성해야함
- 프로그래머의 문서는 명확한 규칙과 조건으로 구현가능한 형태로 번역하는 문서에 가까움

## Chapter 08. 이 책에서 작성할 상세 기획서의 최종 형태
- 이 책의 목표는 프로그래머가 직접 사용할 수 있는 게임 상세 기획서 한벌을 완성하는 것
- 상세 기획서의 목록은 게임 개요, 핵심 플레이 루프, 시스템 기획, UI 기획, 레벨 기획, 데이터 기획, 예외 조건, AI 개발 요청 프롬프트로 구성됨
- AI에게 전달하기 쉬운 형태를 목표로 하며, 프롬프트의 원본 자료가 됨

# Part 02. 게임 아이디어를 개발 가능한 문장으로 바꾸기

## Chapter 09. 막연한 아이디어가 구현을 어렵게 만든다
- 너무 넓고 모호한 아이디어는 어떻게 구현해야 할지가 애매하여 개발 중 판단 기준이 없음
- 아이디어를 구현할려면 각 기능들을 잘게 쪼게어 설명해야함
- 위에 과정을 통해 막연한 아이디어가 구현 가능한 기획으로 바뀜

## Chapter 10. 게임 콘셉트를 한 문장으로 정리하기
- 게임의 장르, 핵심 재미요소, 핵심 시스템 등 게임 콘셉트를 한 문자으로 정리하는 것이 중요
- 해당 작업을 통해 구체적인 구현 범위가 줄어들며, 해야하는 것과 밀어도 되는 것 그리고 빼야하는 것을 구분하기 쉬워짐
- 개발의 출발점이자 개발 방향이 흔들리지 않게 해주는 기둥이 됨

## Chapter 11. 타깃 유저를 정의해야 기능 범위가 보인다
- 게임을 기획할 때 타깃 유저를 먼저 정의해야함
- 타깃 유저가 누구냐에 따라 필요한 시스템과 불필요한 시스템을 구분 할 수 있음
- 프로그래머 관점에서 타깃 유저가 기능 제한의 기준이 됨

## Chapter 12. 장르를 정하면 필요한 시스템이 보인다
- 장르를 정하면 필요한 기능, 개발 우선 순위, 개발 제외 요소 등이 자연 스럽게 정해짐
- 그에 따라 필요한 코드 구조와 데이터 구조도 달라짐
- 장르가 정해지면 필요한 시스템 목록이 자연스럽게 드러남
- 프로그래머 관점에서 장르는 아키텍처의 방향을 잡는 기준이 됨

## Chapter 13. 참고 게임을 분석하는 프로그래머식 방법
- 프로그래머는 게임을 분석할 때 기능, 규칙, 데이터, UI, 흐름으로 나누어 봐야함
- 프로그래머는 화면을 보면서 필요한 데이터 구조와 이벤트 흐름을 함께 떠올릴 수 있어야 함
- 참고 게임을 분석할 떄 각 요소들을 분석 후 내 게임에 필요한 요소만 골라 작게 적용해야 함
- AI에게도 참고 게임 분석 결과는 좋은 입력 자료가 됨

## Chapter 14. 핵심 재미를 기능 단위로 분해 하기
- 프로그래머는 핵심 재미를 기능 단위로 분해해야 함
- 하나의 경험은 하나의 기능만으로 만들어지는 것이 아니라 여러 작은 기능이 같은 타이밍에 맞물려 만들어지는 경험임
- 핵심 재미를 기능 단위로 분해하면 개발 우선순위도 분명해짐
- AI에게 구현을 요청할 때도 핵심 재미를 기능 단위로 나누어 전달해야함

## Chapter 15. 만들고 싶은 것과 만들 수 있는 것을 구분하기
- 모든 아이디어들을 한 프로젝트에 다 넣으면 무거워 짐으로 지금 만들 수 있는 것을 구분해야 함
- 프로그래머는 기능의 매력뿐 아니라 구현 비용도 함께 생각해야함
- 시간, 실력, 리소스, 플랫폼, 테스트 범위를 고려하여 개발 범위를 정해야함
- 각 기능들을 문서화하는 작업을 통해 얼마나 많은 하위 작업을 요구하는 지 보임
- 그 과정을 통해 지금 필요한 기능과 나중에 추가해도 되는 기능을 나눌 수 있음
- 완성 가능한 범위를 정하는 능력은 좋은 기획의 핵심이며, 작은 게임을 끝까지 완성하게 만드는 현실적인 기준임

## Chapter 16. MVP 기준으로 게임 범위 줄이기
- 게임의 핵심 재미요소를 검증 하기위한 최소한 플레이가능한 형태의 범위를 MVP라 함
- 핵심을 검증할 수 있는 게임으로 이 구조가 재미가 없으면 다른 것을 추가해도 문제가 해결 되지않음
- MVP는 개발 우선순위를 정하는 기준이됨
- 상세 기획서 작성 시에도 모든 기능을 같은 기준으로 적으면 안되며, 필수, 중요, 선택으로 나눠야함
- 필수 기능은 MVP에 포함 시켜야하며, 중요는 게임의 재미를 증가시키지만 없어도 테스트가 가능함
- 모든 기능을 AI에게 요청하면 구조가 복잡해지고 검증하기 어려워 짐으로 MVP를 사용하여 AI를 활용해야함
