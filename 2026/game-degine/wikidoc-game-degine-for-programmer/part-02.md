# Part 02. 게임 아이디어를 개발 가능한 문장으로 바꾸기

## Chapter 09. 막연한 아이디어가 구현을 어렵게 만든다
- 너무 넓고 모호한 아이디어는 어떻게 구현해야 할지가 애매하여 개발 중 판단 기준이 없음
- 아이디어를 구현할려면 각 기능들을 잘게 쪼게어 설명해야함
- 위에 과정을 통해 막연한 아이디어가 구현 가능한 기획으로 바뀜

## Chapter 10. 게임 콘셉트를 한 문장으로 정리하기
- 게임의 장르, 핵심 재미요소, 핵심 시스템 등 게임 콘셉트를 한 문자으로 정리하는 것이 중요
- 해당 작업을 통해 구체적인 구현 범위가 줄어들며, 해야하는 것과 밀어도 되는 것 그리고 빼야하는 것을 구분하기 쉬워짐
- 개발의 출발점이자 개발 방향이 흔들리지 않게 해주는 기둥이 됨

## Chapter 11. 타깃 유저를 정의해야 기능 범위가 보인다
- 게임을 기획할 때 타깃 유저를 먼저 정의해야함
- 타깃 유저가 누구냐에 따라 필요한 시스템과 불필요한 시스템을 구분 할 수 있음
- 프로그래머 관점에서 타깃 유저가 기능 제한의 기준이 됨

## Chapter 12. 장르를 정하면 필요한 시스템이 보인다
- 장르를 정하면 필요한 기능, 개발 우선 순위, 개발 제외 요소 등이 자연 스럽게 정해짐
- 그에 따라 필요한 코드 구조와 데이터 구조도 달라짐
- 장르가 정해지면 필요한 시스템 목록이 자연스럽게 드러남
- 프로그래머 관점에서 장르는 아키텍처의 방향을 잡는 기준이 됨

## Chapter 13. 참고 게임을 분석하는 프로그래머식 방법
- 프로그래머는 게임을 분석할 때 기능, 규칙, 데이터, UI, 흐름으로 나누어 봐야함
- 프로그래머는 화면을 보면서 필요한 데이터 구조와 이벤트 흐름을 함께 떠올릴 수 있어야 함
- 참고 게임을 분석할 떄 각 요소들을 분석 후 내 게임에 필요한 요소만 골라 작게 적용해야 함
- AI에게도 참고 게임 분석 결과는 좋은 입력 자료가 됨

## Chapter 14. 핵심 재미를 기능 단위로 분해 하기
- 프로그래머는 핵심 재미를 기능 단위로 분해해야 함
- 하나의 경험은 하나의 기능만으로 만들어지는 것이 아니라 여러 작은 기능이 같은 타이밍에 맞물려 만들어지는 경험임
- 핵심 재미를 기능 단위로 분해하면 개발 우선순위도 분명해짐
- AI에게 구현을 요청할 때도 핵심 재미를 기능 단위로 나누어 전달해야함

## Chapter 15. 만들고 싶은 것과 만들 수 있는 것을 구분하기
- 모든 아이디어들을 한 프로젝트에 다 넣으면 무거워 짐으로 지금 만들 수 있는 것을 구분해야 함
- 프로그래머는 기능의 매력뿐 아니라 구현 비용도 함께 생각해야함
- 시간, 실력, 리소스, 플랫폼, 테스트 범위를 고려하여 개발 범위를 정해야함
- 각 기능들을 문서화하는 작업을 통해 얼마나 많은 하위 작업을 요구하는 지 보임
- 그 과정을 통해 지금 필요한 기능과 나중에 추가해도 되는 기능을 나눌 수 있음
- 완성 가능한 범위를 정하는 능력은 좋은 기획의 핵심이며, 작은 게임을 끝까지 완성하게 만드는 현실적인 기준임

## Chapter 16. MVP 기준으로 게임 범위 줄이기
- 게임의 핵심 재미요소를 검증 하기위한 최소한 플레이가능한 형태의 범위를 MVP라 함
- 핵심을 검증할 수 있는 게임으로 이 구조가 재미가 없으면 다른 것을 추가해도 문제가 해결 되지않음
- MVP는 개발 우선순위를 정하는 기준이됨
- 상세 기획서 작성 시에도 모든 기능을 같은 기준으로 적으면 안되며, 필수, 중요, 선택으로 나눠야함
- 필수 기능은 MVP에 포함 시켜야하며, 중요는 게임의 재미를 증가시키지만 없어도 테스트가 가능함
- 모든 기능을 AI에게 요청하면 구조가 복잡해지고 검증하기 어려워 짐으로 MVP를 사용하여 AI를 활용해야함
