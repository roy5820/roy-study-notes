# Part 03. 게임 상세 기획서의 기본 구조
## Chapter 17. 상세 기획서에는 무엇이 들어가야 하는가
- `게임 개요`는 전체의 방향을 짧게 설명하며 게임의 모슨을 빠르게 이해할 수 있고, 이후 모든 기획을 판단하는 기준점이 됨
- `핵심 플레이 루프`는 반복하는 기본 행동 흐름을 의미하며, 기능 우선순위를 결정하는 기준이 됨
- `플레이 흐름`은 게임 전체의 흐름도이며, 프로그램의 상태 구조를 설계하는데 도움을 줌
- `시스템별 상세 규칙`은 게임에서 사용되는 주요 시스템들을 나누어 각각 동작 방식을 정리한 것이며, 입력, 조건, 처리, 결과를 정리해야함
- `예외 조건`은 상세 기획서에서 빠진 정상적으로 동작할 수 없는 상황에 대해서 어떻게 처리할지 미리 정해두는 것
- `상태 변화`는 각 상태 별 규칙 및 전환 조건을 정리하는 것으로 상태 머신을 구현할 때 기준으로 사용되며, 구조 설계 시 상태 전환 규칙은 매우 중요한 정보임
- `데이터 구조와 수치`는 게임에서 관리해야 하는 데이터를 표로 정리한 것이며, 어떤 값을 코드에 직접 작성할 것인지, 어떤 값을 데이터 파일이나 테이블로 분리할 것인지 판단하기 쉬워짐
- `계산식`은 계산 기준을 구현 단계 이전에 미리 정리해두는 것이며, 해당 작업을 통해 프로그래머가 계산 방법을 즉흥적으로 결정하는 것을 방지함
- `UI와 사용자 피드백`은 주요 기능에 어떤 UI와 피드백이 필요한지 정리한 것으로, 이벤트 구조를 설계하는 기준이 됨
- `성공과 실패 조건`은 게임 시스템이 언제 끝나는지 명확하게 작성한 것이며, 게임 상태를 변경하는 중요한 기준이됨으로 구체적인 수치와 함께 작성하는 것이 좋음
- `기능 우선순위와 MVP 범위`는 각 기능들의 우선순위에 따라 먼저 구현할 기능과 이후 확장할 기능들을 정리해 놓은 것임
- `테스트 기준`은 각 기능들의 완료 기준을 정리해 놓은 것이며, 구현이 끝났는지 판단할 수 있는 기준이 됨
- `구현 시 결정이 필요한 항목`은 아직 결정되지 않은 내용을 문서에 표시해 두는 것이로 'TODO:`내용`'으로 표기하면 좋음
- 상세 기획서를 `AI 요청에 사용할 개발 정보`로 대체할 수 있음
- 상세 기획서는 구현할 떄 필요한 판단을 줄여주는 문서이므로 너무 복잡하고 완벽하게 작성하려 애쓸 필요 없음
- 상세 기획서의 기본 구조는 위에와 같으나 중요한 것은 형식이 아니라 실제 개발에 필요한 정보가 빠지지 않았는 가임
- 상세 기획서는 게임의 아이디어를 기능과 규칙, 데이터와 조건으로 바꾸어 실제 개발까지 이어주는 문서임

## Chapter 18. 개요 문서와 상세 기획서의 차이
- 개요 문서는 게임 전체 모습을 빠르게 이해할 수 있도록 만든 문서이며, 바로 구현할 수 있는 수준이 아님
- 상세 기획서는 개요 문서의 적은 추상적인 설명을 입력, 조건, 처리, 결과, 예외로 바꾸어 구현 가능한 수준으로 세부 규칙을 풀어낸 문서임
- 개요에서는 기능의 목적과 역할을 설명, 상세 기획서에서는 기능이 어떤 조건과 규칙으로 동작하는지 설명함
- 상세 기획서는 기획과 코드 사이에 위치하는 작업명세서에 가까운 문서
- 개요 문서만 가지고 개발할 경우 프로그래머가 결정해야 할 사항들이 많아져 시스템 끼리 규칙이 달라져 나중에 수정할 가능성이 높아지고 상세 기획서는 이러한 구현 단계의 불필요한 판단을 줄이는 역할을 함
- 반대로 상세 기획서만 가지고 작업할 경우 각 시스템은 잘 설계 되지만 게임의 방향성을 잃을 수 있으므로 반드시 게임 전체 방향을 정의한 개요를 기준으로 상세기획서를 작성해야 함
- 반드시 개요문서와 상세문서가 하나일 필요는 없고, 프로젝트의 규모에 따라 나누는 것이 중요함
- 중요한 것은 문서의 개수가 아니라 정보의 역할과 계층을 구분하는 것
- AI에게 제공할 때 `개요 문서`는 AI가 프로젝트 전체를 방향을 이해할 수 있도록 하고, 상세 기획서는 AI가 보다 구체적인 구조나 코드를 제안할 수 있게함
- 개요 문서로 게임의 전반적인 방향을 잡고, 그 뒤에 상세 기획서는 개요 문서를 기준으로 각 기능들을 구체화 해야함으로 개요 문서와 상세 기획서는 각각의 독립 문서가 아님

## Chapter 19. 게임 개요 작성하기
- 게임 개요는 게임 전체를 압축해서 보여주는 문서이며, 처음 봐도 무슨 게임인지 머릿속에 떠올라야 좋은 개요임
- 구성요소는 아래와 같음
  1. `게임 제목을 적기`: 프로젝트와 문서를 구분하는 기본 정보이며, 아직 정식 제목이 없으면 가칭을 사용해도 됨
  2. `장르 작성하기`: 실제 플레이 방식이 드러나는 수준까지 작성하며, 장르를 통해 필요한 시스템들을 예상할 수 있게됨
  3. `플랫폼 작성하기`: 플랫폼은 게임의 입력 방식, UI 크기, 해상도 등 많은 요소에 영향을 줌으로 개요 단계에서 미리 정하는게 좋음
  4. `타깃 유저 정의하기`: 타깃 유저에 따라 기능 복잡도가 달라지며, 미리 결정해야 추후 기능을 추가할 때 좋은 판단 기준이 됨
  5. `한 문장 콘셉트 작성하기`: 게임의 주요 요소가 들어가 개발의 기준이 되며, 추후 기능 추가나 우선순위를 정할 떄 기준이 됨
  6. `플레이어 목표 작성`: 플레이어 목표가 명확해야 성공과 실패 조건도 정할 수 있음
  7. `핵심 행동 작성하기`: 플레이어의 핵심 행동을 정리하면 어떤 시스템을 우선 구현해야하는지 알 수 있음
  8. `핵심 재미 작성`: 핵심 재미를 작성하는 이유는 개발 우선순위를 결정하기 위해서임
  9. `핵심 플레이 루프 작성`: 핵심 플레이 루프를 작성하면 서로 어떤 기능이 연결되는지 알 수 있고 MVP 범위를 결정하는데 도움을 줌
  10. `한 판의 플레이 흐름 간단하게 적기`: 게임 한 판이 처음부터 끝까지 어떻게 진행되는지 짧게 정리한 것으로, 필요한 씬과 게임 상태 구조를 설계하는 참고 자료로 사용됨
  11. `MVP 범위 작성`: 현재 버전에서 어디까지 만들 것인지 포함하여 작성하며, 개발 중 새로운 기능이 계속 추가되는 것을 줄이는 데 도움이 됨
  12. `이번 버전에서 제외할 내용 작성`: 필요 없는 기능이 아닌 지금 필요없는 기능들을 작성하는 것이며, 무엇을 만들지 정하는 것만큼 뭇을 지금 만들지 않을 것인지 정하는 것도 중요
 - 게임 개요는 게임 전체를 빠르게 이해하는 것이 목표이므로 한페이지 정도가 적당함
 - 게임의 방향과 개발 범위를 짧고 명확하게 고정해 주는 기준 문서가 `개요 문서`임

## Chapter 20. 핵심 플레이 루프 작성하기
- 게임을 구성하는 시스템의 연결 관계를 보여주는 구조도에 가까움
- 핵심 플레이 루프는 다음 플레이를 계속하게 만드는 연결 구조를 포함하며, 행동 > 결과 > 보상 > 변화 > 새로운 행동을 반복하는 구조를 가짐
- 플레이어의 행동 결과가 다음 행동을 만들어낸다는 점이 핵심임
- 플레이어가 실제로 반복해서 경험하는 행동을 중심으로 정리하여 플레이어가 느끼는 반복 경험을 먼저 표현하는 문서임
- 행동과 보상이 연결되어야 다음 해동을 할 이유가 생김, 그러므로 각 단계가 다음 단계로 이어지는 이유도 함께 생각해야함
- 핵심 플레이 루프의 각 단계를 분해하면 자연스럽게 필요한 시스템 목록이 만들어짐
- 플레이어 관점에서 의미 있는 행동의 묶음으로 정리하는 것이 좋으며 너무 길어지면 핵심이 흐려짐으로 처음에는 4~6단계 정도로 정리하는 것이 좋음
- 게임 전체를 대표하는 핵심 루프 하나를 정의하고 필요한 경우 시스템별 세부 루프(전투 루프, 성장 루프, 전체 진행 루프 등)를 추가하는 방식을 추천
- 플레이어는 여러 루프(몇 초 단위의 전투 루프, 몇 분 단위의 성장 루프, 한 판 단위의 전체 루프 등)를 경험함으로, 게임 규모가 커지면 이런 짧은 루프와 긴 루프의 관계도 살펴볼 필요가 있음
- MVP에서는 핵심 루프를 테스트하는 것이 주 목적이며, 핵심 루프의 포함된 기능들은 모두 MVP에 포함되어야 함
- 한 번의 반복이 다음 반복을 조금이라도 다르게 만들어 주는 지가 중요하며, 보상이 다음 행동의 조건이나 선택지의 영향을 주어야 루프가 강해짐
- AI를 활용해 시스템을 설계할 때 핵심 플레이 루프를 제공하면 Ai도 기능 하나만 보는 것이 아니라 앞뒤 시스템과 관계를 고려하기 쉬어짐
- 핵심 플레이 루프는 게임의 핵심 경험과 필요한 시스템, 개발 우선순위를 연결하는 기준임
- 각 기능이 왜 존재하고 다음 기능과 어떻게 연결되어 하나의 반복 경험을 만드는지 보여주어야하는데, 핵심 플레이 루프 작성은 이러한 각 여러 기능을 하나의 흐름으로 연결

## Chapter 21. 주요 시스템 목록 작성하기
- 주요 시스템 목록은 전체 게임을 구현 가능한 단위로 나누는 첫 번째 구조화 작업임
- 모든 기능을 독립적인 시스템으로 생각하면 전체 구조가 복잡해짐으로 같은 목적을 가진 기능들 끼리 묶어서 생각하면 좋음
- 기능은 하나의 동작이고 시스템은 여러 기능이 모여 하나의 역할을 수행하는 구조임
- 핵심 플레이 루프를 기반으로 각 단계를 시스템으로 바꾸어 주요 시스템 목록을 작성하는 것이 좋음
- 시스템은 단순히 존재하는 기능이 아니라 플레이어 행동과 연결되어 핵심 플레이 루프를 지원하는 역할을 가져야함
- 시스템 마다 목적을 한 줄 정도로 작성하고, 각 시스템 어떤 주요 기능을 포함하는지 간단히 작성하면 나중에 시스템별 상세 기획성 작성시 쉬워짐
- 각 시스템 별로 필요한 데이터도 함께 정리하면 추후 개발 시 어떤 값을 코드 내부에 둘지, 데이터 파일이나 테이블로 분리할지 판단하기 쉬워짐
- 시스템 목록을 작성하면서 관련 UI도 함꼐 적어두어야 시스템 구현과 UI 작업이 따로 놀지 않음
- 각 시스템은 독립적으로 존재하지않음으로 시스템 목록을 작성한 후 각 시스템별 연결된 시스템 관계도를 작성하면 프로그램 구조를 설계할 때 도움이 됨
- 프로젝트의 규모의 따라 각 기능별로 시스템을 묶거나 나누는 것이 좋음, 처음부터 완벽한 구조를 만드는 것보다 현재 프로젝트를 이해하기 쉬운 정도로 나누는 것이 중요
- 모든 기능들을 한번에 구현할려고 하면 개발 범위가 너무 커짐으로 MVP 시스템과 확장 시스템을 구분하는 것이 좋으며, 확장 시스템은 삭제된 기능이 아닌 개발 순위에서 뒤로 미룬 시스템임
- MVP 시스템 안에서도 시스템 사이의 의존 관계에 따라 우선순위를 정하는 것이 좋으며, 각 시스템 별로 의존 관계를 확인 하는 것이 중요함
- 하나의 시스템이 하나 클래스와 대응하는 것이 아님, 먼저 책임 관계를 정리하고 이후 구현 단계에서 적절한 클래스 구조를 설계하는 것이 좋음
- 시스템 별 상세기획서 양식을 미리 작성하면 이후 상세 기획과 구현을 연결하기 쉬워짐
- 전체 시스템 목록을 한눈에 보기 좋게 정리하면 프로젝트의 전체 구조를 상당 부분 파악하기 좋음
- 시스템 목록은 한번 정하고 고정하는 문서가 아니라 계속 수정할 수 있는 문서임으로 프로젝트 구조를 지속적으로 점검하는 문서임
- AI에게도 큰 하나의 게임을 요청하는 것 보다 작은 시스템을 순서대로 요청하는 편이 구현결과를 관리하기 쉬워짐
- 주요 시스템 목록은 필요한 시스템을 찾고, 각 시스템 별 열할과 관계, 우선순위를 정리해 개발 가능한 구조로 바꾸는 문서

## Chapter 22. 화면 목록 작성하기
- 화면 목록 작성은 플레이어가 게임과 상홍작용하는 전체 구조를 정리한 문서임
- 플레이어의 전체 흐름을 통해서 필요한 기본적인 화면 목록을 만들 수 있으며, 게임 장르적 특징과 규모에 따라 화면을 추가하면 됨
- 게임 UI는 `전체 화면`, `HUD`, `팝업`으로 구성됨
- `전체화면`은 게임 화면 대부분을 차지하고 현제 상태를 대표하는 화면이며 다른 전체 화면으로 이동하면서 게임의 큰 흐름이 진행됨
  - 타이틀, 메인메뉴, 캐릭터 선택, 스테이지 선택, 결과 화면 등이 이에 해당 됨
- `HUD`는 플레이 중 계속 표시되는 정보이며 플레이어가 게임 상태를 즉시 확인하기 위한 UI임
  - 체력, 경험치, 스킬 쿨타임, 미니맵 등이 여기 해당 됨
- `팝업`은 현재 화면 위에 일시적으로 표시되는 UI임
  - 일시정지, 능력 선택, 아이템 상세 정보, 구매 확인, 설정, 경고 메시지 등이 여기에 해당 됨
- 화면 목록 작성 시 이름만 적어서는 실제 UI를 구현하기 부족함으로 최소한 `화면의 목적`, `표시할 데이터`, `버튼과 입력`, `연결되는 시스템`, `진입 조건`, `종료 조건`, `이동할 다음 화면`이 포함되어야 함
- `화면의 목적`: 각 화면이 왜 존재하는지 한 문장으로 설명하는 것이 좋으며, 목적이 명확하면 필요없는 UI 요소를 줄이기 쉬워짐
- `화면에 표시할 데이터`: 화면마다 어떤 데이터를 표시하는지 정리해야 어떤 시스템에서 UI로 데이터를 전달해야 하는지 알 수 있음
- `버튼과 입력`: 화면에 플레이어가 사용할 수 있는 입력 요소와 각 버튼을 눌렀을 때 무엇이 발생하는지 정리해야 어떤 시스템을 호출해야 하는지 알기 쉬워짐
- `화면 전환 흐름 작성`은 화면 사이의 이동 관계를 정리하는 것으로 해당 작업을 통해 게임 상태 관리도설계하기 쉬워짐
- 게임 상태(Title, MainMenu, Playing, Paused, GameOver 등)마다 표시할 UI를 매핑해 놓으면, 상태 전환 시 UI 표시·숨김과 로직 처리(입력 차단, 적 정지 등)가 명확하게 연결됨
- `팝업의 우선순위도`는 여러 팝업이 동시에 열릴 경우 하나만 보여줄지 또는 여러 팝업이 떠있을 경우 어떤 UI가 다른 UI보다 우선하는지 등 중요한 규칙을 정리한 것
- 각 팝업(일시정지 화면, 능력 선택 화면 등)을 표시 했을 때 게임 입력(플레이어 조작 차단 등)과 상태(게임 진행 정지, UI 입력 허용 등)를 어떻게 처리할지 정의해야함
- 화면이 너무 늘어나면 구현 범위가 늘어남으로 UI 역시 MVP 관점에서 범위를 관리해야 함
- MVP에 필요한 화면과 이후 추가하는 화면을 구분하여 작업하는 것이 개발 범위를 줄일 수 있어 좋으며, 특히 초기 버전에서는 핵심 플레이 루프와 직접 연결되는 화면을 우선 구현하는 것이 중요함
- 화면별로 구현 난이도가 다름으로 각 화면의 기능까지 함께 살펴봐야 실제 UI 개발 규모를 예상할 수 있음
- 화면이 많아지면 표로 작성하는 것이 관리하기 쉬우며, UI 규모와 MVP 범위를 한눈에 파악하기 좋음
- 필요하면 중요한 화면은 별도의 상세 기획을 작성하면, 실제 구현에 필요한 요구사항이 상당히 명확해짐
- UI 디자인과 UI 기획을 구분하는 것이 중요하며, UI 기획에서는 기능과 흐름을 먼저 결정하고 시각적 디자인은 그 다음에 구체화 하는 것이 좋음
- AI에게 화면 단위로 요청하면 처리해야할 범위가 명확해지고 결과를 검증하기 쉬워짐
- 화면 목록은 플레이어 경험의 흐름이며, 플레이어가 화면 사이를 어떻게 이동하는지 함께 살펴봐야 함
- 화면 목록은 UI와 게임 시스템을 연결하며, 각 화면이 왜 필요한지, 무엇을 보여주는지, 어떤 입력을 받는지, 어떤 시스템과 연결되고 어디로 이동하는지 설명하는 문서임
