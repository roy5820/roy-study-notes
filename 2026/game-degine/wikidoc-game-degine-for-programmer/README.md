# Part 01. AI 시대, 왜 프로그래머에게 기획서가 필요한가
## Chapter 01. 바이브 코딩 시대의 게임 개발 변화
- 우리 아이디어를 ai를 통해서 개발하기 위해서는 무엇이, 어떻게, 왜 가 적용된 상세 기획서가 필요함
- ai 시대가 돌입 되면서 프로그래머는 만들고자 하는 기능을 정확히 설명하고 이해시키는 능력이 중요해짐
- 이러한 이유로 상세 기획서 작성은 개발의 기준이며, 매우 중요한 과정이 됨

## Chapter 02. 코드를 잘 쓰는 것만으로는 부족한 이유
- 게임은 단순히 여러 기능을 구현한다고 완셩되지 않으며, 각 기능들이 어떤식으로 연결되어 작동되는 지 고려해야함
- 구현 대상의 세부적인 규칙과 조건들을 작성하지 않으면 개발 과정 중에서 즉흥적으로 결정하게 되어 코드 구조가 흔들림

## Chapter 03. 프로그래머가 기획을 이해해야 하는 순간
- 요구사항이 모호할 때 상세한 내용을 정하지 않고 개발하게 되면 프로그래머가 임의로 규칙을 정하게 되며, 이로인하여 기획의도와 달라질 수 있음
- 게임의 기능은 대부분 독립적이지 않고 2개 이상의 기능들이 연결 되어 있으므로 어떤 규칙을 우선해야 하는지 이해하지 못하면 기능간의 충돌로 새로운 문제가 발생함
- 프로그래머는 기획서를 그대로 코드로 옮기는 것에 그치지 않고, 구현하면서 기획의 문제가 발견될 때 기획의 문제로 되돌려 생각해야함
- 기술적인 제약이 발견될 때 단순히 안된다 하는 것에 그치지 않고, 기획 의도를 이해하여 다른 방안을 제시할 수 있어야함
- 게임의 요구사항을 구현 가능한 단위로 분해할 수 있어야 AI에게 좋은 구현을 요청할 수 있음
- 프로그래머에게 필요한 기획 이해력이란 요구사항을 실제 구현할 수 있는 수준까지 구체화하는 능력임

## Chapter 04. 기획자가 없는 프로젝트에서 생기는 문제
- 기획자가 없는 프로젝트에서는 기능을 즉흥적으로 구현하게 되며, 이로인하여 기능간의 충돌이 발생함
- 개발함에 있어서 간단한 기준(문서)이라도 존재해야하며, 누군가는 기획을 해야함

## Chapter 05. AI에게 일을 시키려면 먼저 구조화해야 한다
- 모호한 요청은 모호한 결과를 만들며, 요구사항을 분리해서 설명해야함
- 기능을 구현 단위로 나누어야하며, 상태와 조건을 명확하게 해야함
- AI에게 요청을 하기 전에 먼저 해야할 가장 중요한 일은 무엇을 만들 것인지 구조화하는 일임

## Chapter 06. 상세 기획서는 개발을 느리게 만드는 문서가 아니다.
- 구현하는 기능에 따라 간단하게 혹은 상세하게 작성해도 됨
- 상세 기획서는 생각을 기록하는 도구이며, 이를 통하여 현재 결정된 사항 확인을 통한 빠진 조건 발견, 기능 변경 시 영향을 받은 부분 체크 등 불필요한 작업을 줄이기 위한 문서임
- 필요한 만큼 작성하는 것이 핵심

## Chapter 07. 프로그래머가 쓰는 기획서와 기획자가 쓰는 기획서의 차이
- 프로그래머의 기획서는 구현 가능한 수준으로 게임의 규칙을 정리한 것
- 게임의 의도 설명, 구체적인 규칙, 상태와 조건, 데이터, 예외 상황, 구현 우선순위 등이 포함된 기획서와 설계서 중간에 가까운 성격을 띰

## Chapter 08. 이 책에서 작성할 상세 기획서의 최종 형태
- 게임 전체를 몇 개의 영역으로 나누고 하나씩 구체화하면 되고, 구조는 아래와 같음
- 게임 개요 -> 핵심 콘셉트 -> 플레이어의 목표 -> 핵심 플레이 루프 -> 조작 방법 -> 플레이어 시스템 -> 전투 시스템 -> 적 시스템
- -> 아이템 시스템 -> 성장 시스템 -> 게임 진행 구조 -> UI와 화면 흐름 -> 데이터 정의 -> 상태와 예외 조건 -> 구현 우선순위 -> AI 구현 요청을 위한 요구사항
- 완성된 기획서는 개발의 기준이 되며, 게임 아이디어를 구현 가능한 수준까지 조금씩 구체화하는 것이 중요함

# Part 02. 게임 아이디어를 개발 가능한 문장으로 바꾸기
## Chapter 09. 막연한 아이디어를 개발 가능한 문장으로 바꾸기
- 막연한 아이디어는 개발 중 판단 기준이 사라져, 계속 새로운 아이디어로 인하여 기능이 추가되고 프로젝트 기간과 개발 기간이 함꺠 늘어나며, 이를 스코프 크리프라 부름
- AI는 정리된 요구사항을 빠르게 구체화하고 확장하는 도구로 활용하는 것이 좋음
- 아이디어를 개발 가능한 단위로 나누느 과정을 통해 어떻게 구현할 것인지 판단할 수 있으며, 상세 기획서가 필요한 이유임

## Chapter 10. 게임 콘셉트를 한 문장으로 정리하기
- 잘 만든 게임 콘셉트는 개발의 기준점이 되며 개발 범위, 개발 우선순위 관리가 더 쉬어짐
- 느낌보다 실제 플레이어가 실제로 무엇을 하는지로 행동을 설명하는 문장에 가까운 형태로 구성해야하며, [핵심행동], [목표], 장르 또는 플레이 방식]이 들어가야함
- 상세 기획을 시작하기 위한 첫 번째 기준점이며, 그 문장을 통해서 기능과 시스템으로 나눌 수 있음

## Chapter 11. 타깃 유저를 정의해야 기능 범위가 보인다
- 장르가 같아도 타깃 유저에 따라 기능이 달라지며, 게임 난이도, 기능 제한 등을 결정하는 기준이 됨
- 타겟 유저는 실제 플레이 방식과 사용 환경 등 구체적으로 정의해야하며, 상세 기획서에 타깃 유저를 기재해야함

## Chapter 12. 장르를 정하면 필요한 시스템이 보인다
- 장르를 구체적으로 잘 정하면, 게임의 필요한 기능과 불필요한 기능, 개발 우선 순위, 프로그램 구조, 데이터 구조 등을 결정하는데 있어서 쉬어짐
- 장르는 실제 플레이 방식이 드러나는 수준까지 구체화하는 것이 좋으며, 장르를 섞을 경우 주장르와 보조 장르를 분리하는 것이 우선순위 결정을 쉽게 만들어줌

## Chapter 13. 참고 게임을 분석하는 프로그래머식 방법
- 참고 게임 분석은 감상을 구현 항목으로 결과를 원인으로 살펴보는 과정이며, 해당 과정을 통해 전반적인 게임 구조, 흐름, 데이터, 상태도 같이 보이게 됨
- 게임을 똑같이 만드는 것이 아닌 좋은 플레이 경험이 어떤 시스템과 규칙을 통해 만들어 졌는지 이해하는 것이 핵심임
- 모든 기능을 분석할 필요는 없으며 현제 개발 중인 부분에 대해서만 북석해도 좋음, 비슷한 장르의 게임을 여러개 북석하는 것이 좋음

## Chapter 14. 핵심 재미를 기능 단위로 분해하기
- 게임에서 재미는 하나의 기능이 아닌 여러 기능들이 적절한 타이밍으로 연결되어 만들어진 경험임
- 핵심 재미를 기능 단위로 분해할 때 입력, 규칙, 결과, 피드백으로 분리해서 작업
- 핵심 재미를 먼저 개발하여 재미를 검증한 후 보조 기능을 개발하는 것이 좋음
- 핵심 재미를 기획서에 분리(핵심 기능, 전투 피드백, 성장 피드백)하여 기능 목록을 만들어 관리해야함

## Chapter 15. 만들고 싶은 것과 만들 수 있는 것을 구분하기
- 기능 하나를 구현하는데 많은 작업이 필요할 수 있음, 기능이 추가되면 연결된 다른 기능들도 수정해야 하며, 다순 개발 시간 뿐 아니라 소요되는 그래픽 리소스, 사운드 등도 고래해야함
- 개발자의 능력도 개발 범위에 포함되며 새롭게 배우는 기술의 개수도 제한하는 편이 좋음
- 플랫폼 자체도 구현 가능한 기능 범위를 결정하는 조건임
- 상세 기획서는 기능을 분류(반드시 필요한 기능, 있으면 좋은 기능, 나중에 고려할 기능)하여 기능들을 삭제하거나 줄이기 위한 문서이기도 함
- 게임을 완성하는 것이 최우선이며, 이를 위해서 중요한게 완성 가능한 범위를 먼저 정한 뒤 현재 조건에서 핵심 재미를 끝까지 구현할 수 있도록 범위를 정한 기획임

## Chapter 16. MVP 기준으로 게임 범위 줄이기
- MVP는 '최소한으로 실행 가능한 제품'으로 게임의 핵심 루프, 핵심 재미요소를 검증하기위한 최소한으로 기능이 구현하는 것임
- 핵심 재미요소가 재미가 없거나 문제가 있으면 다른 기능들을 추가, 수정한다고 해서 문제가 해결되지 않기 때문에 MVP를 기준으로 핵심 기능들을 개발한 후 검증하는 작업이 매우 중요함
- 기능을 필수 기능, 중요 기능, 선택 기능으로 분류할 수 있으며 필수 기능이 MVP, 중요기능은 MVP 이후 우선적으로 개발 해야하는 기능이며, 선택 기능은 핵심 재미 검증에는 직접 필요하지 않는 기능 들임
- MVP는 최종 결과물이 아니기에 각 버전별로 재미요소를 검증하는 것이 중요하며, 상세 기획서에 MVP 범위를 따로 표시하여 지금 당장 구현할 필요없는 것들은 다음 버전으로 미루어도 됨

# Part 03. 게임 상세 기획서의 기본 구조
## Chapter 17. 상세 기획서에는 무엇이 들어가야 하는가
- `게임 개요`는 전체의 방향을 짧게 설명하며 게임의 모슨을 빠르게 이해할 수 있고, 이후 모든 기획을 판단하는 기준점이 됨
- `핵심 플레이 루프`는 반복하는 기본 행동 흐름을 의미하며, 기능 우선순위를 결정하는 기준이 됨
- `플레이 흐름`은 게임 전체의 흐름도이며, 프로그램의 상태 구조를 설계하는데 도움을 줌
- `시스템별 상세 규칙`은 게임에서 사용되는 주요 시스템들을 나누어 각각 동작 방식을 정리한 것이며, 입력, 조건, 처리, 결과를 정리해야함
- `예외 조건`은 상세 기획서에서 빠진 정상적으로 동작할 수 없는 상황에 대해서 어떻게 처리할지 미리 정해두는 것
- `상태 변화`는 각 상태 별 규칙 및 전환 조건을 정리하는 것으로 상태 머신을 구현할 때 기준으로 사용되며, 구조 설계 시 상태 전환 규칙은 매우 중요한 정보임
- `데이터 구조와 수치`는 게임에서 관리해야 하는 데이터를 표로 정리한 것이며, 어떤 값을 코드에 직접 작성할 것인지, 어떤 값을 데이터 파일이나 테이블로 분리할 것인지 판단하기 쉬워짐
- `계산식`은 계산 기준을 구현 단계 이전에 미리 정리해두는 것이며, 해당 작업을 통해 프로그래머가 계산 방법을 즉흥적으로 결정하는 것을 방지함
- `UI와 사용자 피드백`은 주요 기능에 어떤 UI와 피드백이 필요한지 정리한 것으로, 이벤트 구조를 설계하는 기준이 됨
- `성공과 실패 조건`은 게임 시스템이 언제 끝나는지 명확하게 작성한 것이며, 게임 상태를 변경하는 중요한 기준이됨으로 구체적인 수치와 함께 작성하는 것이 좋음
-
